# spetest
# Repository Agent Rules

このファイルは、本リポジトリで作業するAIエージェント共通の作業ルールを定義する。

Kiro、GitHub Copilot、Devinその他のAIツールに依存しない共通ルールは、
原則としてこのファイルを正本とする。

---

## 1. 基本原則

- 原則として日本語で説明・設計・ドキュメントを作成する。
- 一般的な技術用語を除き、不必要な英語表現や独自用語を作らない。
- 独自概念を導入する場合は、以下を明確にする。
  - 日本語での定義
  - 導入する理由
  - 既存概念では表現できない理由
  - 具体例
- 「将来必要になるかもしれない」という理由だけで抽象化・拡張ポイントを追加しない。
- 実際に複数の具体的ユースケースが存在しない抽象化は避ける。
- 既存実装を仕様の正解と決めつけない。
- 推測を事実として扱わない。
- 不明点を勝手な仮定で埋めて実装を進めない。

---

## 2. 情報の正本

情報の種類ごとに、以下を参照先とする。

| 情報 | 正本・参照先 |
|---|---|
| 現在有効なシステム仕様 | `docs/system/` |
| 現在の実装・実際の動作 | ソースコード、DDL、設定ファイル、ビルド定義等 |
| 設計・方針の意思決定 | `docs/decisions/` |
| 調査結果・証拠 | `docs/investigations/` |
| 要件確定前の構想・検討 | `docs/plans/` |
| 変更案件の要求・設計・タスク | `.kiro/specs/` |
| 再利用可能な作業手順 | `.agents/skills/` |

`docs/plans/`、`docs/investigations/`、`.kiro/specs/`を
現在のシステム仕様の正本として扱ってはならない。

コード・DDL・設定と`docs/system/`が矛盾する場合は、
どちらかを無条件に正しいものとして扱わず、原因を調査する。

矛盾を解消した場合は、必要に応じて実装または`docs/system/`を更新し、
現在仕様と実装の整合性を回復する。

---

## 3. 作業開始ルール

作業開始時に、以下の基準で作業モードを判断する。

### Direct

以下をすべて満たす場合は直接作業してよい。

- 単純かつ局所的な変更である
- 変更内容と期待結果が明確である
- 影響範囲が既知である
- 新たな設計判断を必要としない

例:

- typo修正
- formatting
- 明白なコメント修正
- 既存パターンに従う軽微な修正

### Spec

以下を満たす場合はSpecを作成する。

- 目的が明確である
- Scopeが明確である
- 期待成果が明確である
- 受入条件を定義できる
- 設計または複数ファイルにまたがる実装が必要である
- 設計を左右する重大なUnknownが残っていない

### Planning

以下の場合は実装やSpec作成を急がず、Planningを行う。

- 何を実現したいのかが曖昧
- 目的が曖昧
- Scopeが曖昧
- 期待成果が曖昧
- 複数の実現方針から選択する必要がある
- そもそも何を作るべきか整理が必要

Planningの詳細手順はPlanning Skillに従う。

成果物は原則として以下に保存する。

`docs/plans/<topic>/`

### Investigation

以下の場合はInvestigationを行う。

- 現在仕様が不明
- コードの実際の挙動が不明
- 依存関係が不明
- 影響範囲が不明
- 設計判断に必要な事実が不足している
- PlanningまたはSpecを進めるための根拠が不足している

Investigationの詳細手順はInvestigation Skillに従う。

成果物は原則として以下に保存する。

`docs/investigations/<topic>/`

Planning中に調査が必要になった場合はInvestigationへ移り、
調査結果を反映してPlanningへ戻ってよい。

PlanningとInvestigationは固定的な直列工程ではない。

---

## 4. Implementation Gate

重大なUnknownが残っている状態ではimplementationを開始してはならない。

特に以下が不明な場合は、原則として実装へ進まない。

- 何を解決する変更なのか
- In Scope / Out of Scope
- 主要な受入条件
- 重大な影響範囲
- 設計を左右する既存挙動

Unknownが事実確認によって解消できる場合はInvestigationを行う。

要求や方針の整理が必要な場合はPlanningを行う。

---

## 5. Specの位置づけ

Specは「現在仕様の正本」ではなく、
今回の変更内容を定義するChange Contractとして扱う。

原則として以下の流れで管理する。

Planning / Investigation
↓
Spec
↓
Implementation
↓
必要に応じて `docs/system/` を更新

実装完了後、変更によって現在仕様が変わった場合は
必ず`docs/system/`への反映要否を確認する。

---

## 6. Decision Record

以下のような重要かつ長期的な判断を行った場合は、
Decision Recordを作成する。

- アーキテクチャ上の重要な選択
- データ設計上の重要な選択
- 複数の有力な選択肢から1つを採用した場合
- 後から変更するコストが大きい判断
- 将来「なぜこの方式なのか」が問題になりそうな判断
- 複数システム・複数チームに影響する方針

Decision Recordの詳細手順はDecision Record Skillに従う。

成果物は以下に保存する。

`docs/decisions/`

単純な実装詳細や一時的な判断については、
不要なDecision Recordを作成しない。

---

## 7. Skills

再利用可能な作業手順の正本は以下とする。

`.agents/skills/`

代表的なSkill:

- `planning`
- `investigation`
- `decision-record`

Skillには以下を定義する。

- いつ使用するか
- 目的
- 作業手順
- 禁止事項
- 完了条件
- 必要なテンプレート・スクリプト・参考資料

AGENTS.mdにSkillの詳細手順を重複して記載しない。

ツール固有のSkill配置が必要な場合は、
`.agents/skills/`を正本として機械的に同期・生成する。

同じSkillを複数箇所で手動編集してはならない。

---

## 8. ドキュメント管理

以下の役割を混同しない。

- `docs/system/`
  - 現在どうなっているか

- `docs/decisions/`
  - なぜその方針を選んだか

- `docs/investigations/`
  - 何を調べ、何が分かったか

- `docs/plans/`
  - 何を実現したいか、何が未確定か

- `.kiro/specs/`
  - 今回何を変更するか

古い情報を現在仕様として残さない。

単なる履歴保存を目的とした`archive`を乱用しない。
履歴が必要な場合はGit履歴を利用する。

---

## 9. 実装時の原則

- 変更前に関連コード・仕様・テストを確認する。
- 必要最小限の変更を優先する。
- 不要なリファクタリングを同時に行わない。
- 新しい依存ライブラリやフレームワークを安易に追加しない。
- 既存の設計・命名・テストパターンを優先する。
- 変更に対応するテストを追加または更新する。
- 実装と現在仕様が変わる場合は`docs/system/`の更新要否を確認する。
- 重要な設計判断が発生した場合はDecision Recordの作成要否を確認する。

---

## 10. 安全性

以下の操作を独断で実行してはならない。

- 強制push
- Git履歴を破壊する操作
- 広範囲のファイル削除
- データベース・スキーマ等の破壊的操作
- 本番環境への変更
- 認証情報・秘密情報の出力またはコミット
- 大量ファイルを対象とする意図不明な自動変更

破壊的操作が必要な場合は、
実行前に目的・対象・影響を明確にする。

---

## 11. 作業完了条件

作業完了前に以下を確認する。

- 依頼された目的を満たしている
- Scope外の不要な変更をしていない
- 必要なテスト・検証を実施した
- 重大なUnknownを残したまま完了扱いにしていない
- 現在仕様が変わった場合、`docs/system/`を更新した
- 重要な判断が発生した場合、Decision Recordの要否を確認した
- 調査結果と推測を混同していない
- 一時的な作業メモを正本として残していない
