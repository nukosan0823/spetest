# 日本語技術文書の執筆と推敲

日本語の技術文書を執筆または推敲するときは、技術的な意味を固定したうえで、構成、論証、表現の順に整える。

## 規則の優先順位

規則が衝突するときは、次の順序で優先する。

1. 技術的正確性と原文の意味
2. ユーザーが指定した目的、対象読者、形式
3. 根拠、不確実性、引用、コード、数値、識別子の保持
4. 論証と用語の一貫性
5. 読み手の負荷
6. 表記とハウススタイル

下位の規則を守るために、上位の情報を削除、変更、断定してはならない。

## 作業モード

依頼を次のいずれかへ分類する。

- **新規執筆**：ユーザーが提供した情報と、使用を許可された確認済みの情報源だけを使う。一般知識だけで具体的な事実、数値、原因、機構を補わない。
- **推敲、校正、校閲、リライト**：原稿を閉世界として扱う。ユーザーが調査や情報追加を明示しない限り、原稿にない事実、原因、根拠、機構、例を追加しない。論理の不足は、主張を狭める、未確認と示す、または確認事項として返すことで処理する。
- **レビュー**：問題、根拠、修正案を示す。ユーザーが書き換えも求めている場合だけ完成稿を作る。

## 文書種別の判定

作業前に、文書の種類、対象読者、目的、求められる出力を判定する。

- **説明型長文**：技術書、章、記事、チュートリアル、概念解説が該当する。[技術書と解説記事のスタイル](references/technical-book-style.md)を最初から最後まで読み、本文の規則と併用する。
- **実務文書**：手順書、仕様書、ADR、障害報告、API リファレンス、監査証跡が該当する。識別子、数値、順序、結論先行、既存テンプレートを保持する。ユーザーが書籍調の文章を求めた場合を除き、書籍向けの参照規範は読み込まない。
- **短文**：チャット、メール、スライド文言、箇条書きだけの回答が該当する。ユーザー指定の形式を優先し、長文向けの段落規則を機械的に適用しない。

文書種別、対象読者、目的の違いによって結果が大きく変わり、依頼から判定できない場合だけ確認する。

## 実行手順

1. 依頼と原稿を読み、作業モード、文書種別、対象読者、目的、出力形式を特定する。
2. 変更してはならない情報を抽出する。技術的主張、根拠、不確実性、引用、コード、数値、識別子、用語を対象とする。
3. 段落の役割と論証の順序を設計する。主張、根拠、機構、例、限定、結論の関係を整理する。
4. 構成、論証、表現の順に執筆または推敲する。
5. 最終チェックを実行する。違反や意味の変化があれば修正し、チェックを繰り返す。

## 意味と証拠の保持

- 推敲、校正、校閲、リライトでは、原文にない事実、原因、根拠、機構、引用、数値、例を追加しない。
- もっともらしい一般知識を使って、原文の論理的な不足を滑らかに補わない。
- 引用、コード、コマンド、パス、API 名、設定値、固有の識別子を、ユーザーの指示なしに書き換えない。
- 事実未確認の可能性、ログからの推定、作中人物の認識、読者が抱きそうな疑念、反実仮想を断定へ変えない。
- 「かもしれない」「だろう」「ようだ」「可能性がある」は、根拠なく主張を弱めている場合だけ削る。
- 確認していないことを、確認したかのように書かない。
- 検出、保証、解決を無条件に実現できるかのように書かない。成立条件または限界を示す。
- 出典や原文だけでは確定できない点は、不明または未確認であることを保つ。

## 段落と論証

- 一つの段落には一つのトピックを置く。
- 段落の最初の文で、その段落が扱う対象または問いを示す。
- 前の段落との関係が自明でない場合だけ、接続表現で論理関係を示す。
- 新しい概念は、対象、働き、既存概念との差分を示してから定義する。ただし、用語集、API リファレンス、直接的な定義が読み手の負荷を下げる場面では辞書型の定義を使ってよい。
- 読者が立てそうな誤った解釈は、否定する命題を正確に示してから、本当の理由を述べる。
- 「A ではなく B」と否定するときは、A を否定する根拠を添える。
- 複数の要因がある事象を単一の原因へ還元しない。要因と、それぞれを説明する根拠を対応づける。
- 異なる決定、原因、問題を「同じ」とまとめない。必要な粒度へ分解する。
- 因果を主張するときは、A から B が生じる機構を示す。
- 例が主張の一部だけを支える場合は、主張の範囲を例に合わせて狭める。
- 説明型の論証で譲歩や限定を途中に置く場合は、その後で論を進める。実務文書では、未解決事項、制約、残存リスクを最後に置いてよい。
- 前方参照を置く場合は、参照先で論点が回収されることを確認する。
- 章や節をまたいで、分類、定義、用語の地位を一致させる。

## 読み手の負荷

- 対象を具体的に指す。「AI」「ツール」「仕組み」のような広い語だけで済ませない。
- 抽象的な表現の指示対象が一意に決まらない場合は、その場で対象を特定する。
- 新しい例を追加するときは、前の例との違いと追加する理由を示す。
- 対象読者が確実に補える中間説明だけを省く。初心者が理解に必要とする手順や前提は残す。
- 説明に不要な固有名だけを一般化する。手順の実行、検証、追跡、監査に必要な固有名は保持する。
- 複数の文を一文へ圧縮するのは、意味を失わず、一文が読みにくくならない場合に限る。
- 同じ主張の反復は、同じ論理階層の中で削る。概要、本文、結論がそれぞれ異なる役割を持つ場合は、必要な範囲で再掲してよい。

## 用語と表現

- 初めて使う術語は、使用前または使用直後に対象範囲を定義する。
- 定義した術語は同じ意味で使い続け、曖昧な上位語へ後退しない。
- その分野で慣用されている術語と訳語を使う。
- 結果の羅列や受動態だけで場面を進めず、行為者が重要な場合は主語と動作を示す。
- 中身を増やさない予告、総括、強調、姿勢表明を削る。
- 「重要なのは」「正面から」「多角的」「包括的」「掘り下げる」「言語化する」などは、その語が具体的な情報を加えない場合に削る。
- 「さらに」「また」「加えて」を機械的に連続させない。論理関係に合う接続を選ぶ。
- 空虚な称賛、過剰な劇化、指示対象が曖昧な比喩を使わない。
- 文章の調子を弱めるためだけの推量表現を使わない。ただし、事実上の不確実性は保持する。

## 出力

- ユーザーが修正理由、差分、講評を求めていない場合は、完成した本文だけを返す。
- ユーザーがレビューを求めた場合は、問題、根拠、修正案を対応づける。
- 原稿の情報だけでは修正できない箇所を推測で補わない。必要な確認事項または未確定箇所を明示する。
- 既存の Markdown、見出し階層、コードブロック、脚注、リンク、引用の構造を、変更理由がない限り保持する。

## 最終チェック

完成前に次の項目を確認し、一つでも満たさなければ修正して再確認する。

- [ ] 技術的主張、根拠、不確実性、引用、コード、数値、識別子を保持した。
- [ ] 推敲では、原文にない事実、原因、根拠、機構、例を追加していない。
- [ ] 文書種別と対象読者に合う構成を選んだ。
- [ ] 各段落のトピックと役割を説明できる。
- [ ] 主張、根拠、因果の機構、例、限定が対応している。
- [ ] 異なる問題や原因を一括りにしていない。
- [ ] 用語、分類、定義を一貫して使っている。
- [ ] 曖昧な否定、無条件の保証、空虚な LLM 表現を残していない。
- [ ] 必要な識別子と説明を削っていない。
- [ ] ユーザーが求めていない前置きや講評を追加していない。
