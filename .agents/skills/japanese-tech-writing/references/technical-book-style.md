# 技術書と解説記事のスタイル

この規範は、技術書、章、解説記事、チュートリアルなど、説明型の長文に適用する。
手順書、仕様書、ADR、障害報告、API リファレンスへ機械的に適用しない。
`SKILL.md`の規則と衝突する場合は、`SKILL.md`の優先順位に従う。

## 原稿の整形

- Markdown のソースでは一文ごとに改行し、段落の区切りを空行で示す。
- コード、差分、ログ、設定ファイルの断片をコードブロックで示す。
- 引用文を改変せず、次の形式で示す。出典情報がある場合は引用と対応づける。

  ```markdown
  > 引用文。
  >
  > 出典：著者『書名』、該当箇所
  ```

- 本筋から一段外れる補足は、脚注が使える形式では次のように示す。

  ```markdown
  本文[^label]

  [^label]: 補足。
  ```

- 出版システムにコラム記法がある場合は、その指定を優先する。指定がない Markdown では、次の形式で本文と区別する。

  ```markdown
  > **同値関係としての分類**
  >
  > コラム本文。
  ```

- 定義や分類の列挙には箇条書きを使ってよい。定義する用語を太字にする。
- 用語を初めて定義または導入するときは、その語を太字にする。
- 導入済みの語をメタ言語として話題にするとき、引用、通称には「」を使う。概念を通常の意味で使うだけなら括弧を付けない。
- 用語と定義を並べる箇条書きは、全角コロンを使って「**用語**：説明」と書く。
- 日本語の地の文と見出しでは、em ダッシュ `—`、horizontal bar `―`、二倍ダッシュ「——」を使わない。
- 同格または補足の挿入には括弧を使う。言い換えは句点で二文に分けるか、読点でつなぐ。
- 範囲を示す en ダッシュ `–`、英語の複合語、コード、書誌情報はダッシュ禁止の対象外とする。
- 日本語の並列では中黒を使わない。単一の固有名詞に含まれる中黒は保持する。

## 段落と論証の進行

- 一つの段落を論証の一歩として扱い、一つのトピックだけを置く。
- 調査、報告、検証、評価が一段落に混在する場合は、論理上の役割ごとに分ける。
- 段落の最初の文で、その段落が扱う対象または問いを示す。
- 前の段落との関係が読み手に伝わらない場合は、関係を示す接続表現を置く。すべての段落へ機械的に接続詞を追加しない。
- 新しい概念は、対象、働き、既存概念との差分を示してから定義する。
- 用語集、リファレンス、直接的な定義が理解を早める箇所では、「X は Y である」という定義から始めてよい。
- 物語的に論証を進める節では、反論と疑念を処理してから節の結論を置く。
- 章の概要、エグゼクティブサマリー、ADR など、結論先行が目的に合う形式では結論を先に示してよい。
- 例が作為的に見える可能性への説明は、例の山場を分断しない位置へ置く。
- 誤った解釈を否定するときは、否定する命題を「」で特定し、その理由を示す。
- 「A ではなく B」と書くときは、A では説明できない理由を添える。必要なら反実仮想を使う。
- 譲歩では確認できる事実だけを認める。後で訂正する因果を著者の声で先に断定しない。
- 数値や固有の事実を山場で初めて示す構成は、意図的な叙述が理解を助ける場合だけ使う。
- 前方参照は論証が一段落した位置へ置き、参照先で必ず回収する。
- 複数の概念を上位語でまとめるときは、それらが共通する理由を命名の直前に示す。

## 読み手の記憶負荷

- 後で参照せず、議論にも必要ない固有名だけを一般化する。
- 実行、再現、追跡、監査に必要なファイル名、関数名、識別子は残す。
- 抽象的な表現の指示対象が一意に決まらない場合は、丸括弧による同格挿入などでその場で特定する。
- 新しい例を追加するときは、前の例との違いと追加する理由を先に示す。
- 章や節の導入では、その節の問いと帰結に関係しない詳細を詰め込まない。
- 時刻、HTTP ステータス、カバレッジ率なども、議論、再現、検証に不要な場合だけ省く。
- 対象読者が確実に補える中間説明だけを省く。初心者に必要な前提や手順を削らない。

## 視点と語り

- 例示では結果の羅列だけで済ませず、行為者が重要な場合は主語と動作の連なりを示す。
- 内容に関係しない架空の年齢、経験年数、肩書を人物へ付けない。
- 論証の中で読者を「あなた」と呼ばず、必要なら「開発者」「運用担当者」「読者」のような役割名を使う。
- 二人称の呼びかけは、場面への導入や章の結びなど、意図がある箇所に限る。
- 「AI」「ツール」のような広い語だけで対象を指さず、エージェント、生成モデル、静的解析器など実際の対象を示す。
- 文書内で定義した術語は、その後も同じ語で表す。一般的な上位語へ戻して意味を曖昧にしない。
- 慣用されている術語と訳語を使い、意味の近い漢語を独自に割り当てない。
- 人物そのものへ言及するときは、その分野の慣用表記を使う。人名を冠した概念は定着した名称を優先する。
- 術語の響きを持つ語を、術語でない対象の比喩として流用しない。

## 演出の抑制

- 溜めや修辞疑問は、緊張が理解に寄与する箇所に限る。
- 短い決め台詞を独立段落にする演出を繰り返さない。
- 体言止め、感嘆符、劇的な転回は、議論の山場で効果がある場合だけ使う。
- 太字強調は、初出の定義、誤読を防ぐ否定、節の帰結などに限定する。
- 命令調を避ける必要がある文脈では、作業者の判断として表現する。
- 事故や危険の帰結を必要以上に列挙して煽らない。
- 「A ではなく B だった」という対句を決め台詞として繰り返さない。
- 指示対象が一意に決まらない比喩や、慣用表現を不自然にひねった言い回しを使わない。

## LLM 特有の空句

次の表現は、具体的な情報または論理関係を加えない場合に削る。
語そのものを一律に禁止せず、その文が新しい内容を持つかで判断する。

- **予告と総括**：「重要なのは」「本章では扱う」「ここでは見ていく」「まとめると」「要するに」「〜に他ならない」
- **姿勢表明**：「正面から扱う」「正面から回収する」「正面から見る」
- **空虚な形容**：「不可欠」「核心的」「鍵となる」「根本的」「多角的」「包括的」「総合的」
- **空虚な動詞**：「掘り下げる」「深掘りする」「言語化する」「触れる」「言及する」
- **接続の型**：「〜において」「〜という側面から」「〜の観点から」、「さらに」「また」「加えて」の連続
- **根拠のない緩和と称賛**：「〜と言えるだろう」「〜かもしれない」「非常に」「極めて」「大いに」

推量、仮定、読者の疑念、作中人物の認識を示す緩和表現は残す。
文書で定義した術語を議論に使うことと、空虚な装飾として使うことを区別する。

## 冗長性の管理

- 同じ主張を同じ論理階層で言い換えて繰り返さない。
- 概要、本文、結論が異なる役割を持つ場合は、必要な範囲で同じ主張を再掲してよい。
- 隣接する節の役割が重複する場合は、一方へ統合する。
- 場面を描写した直後に、描写内容をそのまま要約し直さない。必要なら意味づけだけを加える。
- 同じ論理的役割を持つ事実は、一文が読みにくくならない範囲でまとめる。
- 読み手が確実に補える説明だけを省き、対象読者に必要な導出を残す。
- 複数の文を一文へ圧縮するのは、意味と読みやすさを損なわない場合に限る。
- 接続または評価のためだけの文を置かない。
- 想像上の読者との問答や、読者の反応を演じる文章を修辞として繰り返さない。
- 読者が抱きそうな疑問は、メタな枠取りを加えず、必要なら疑問そのものを示す。
- 著者の立場を弁明する断りを置かず、確認できる事実を書く。
- 本文でまだ導入していない概念や文書名を先回りして持ち出さない。

## 見出し

- 見出しは、その節が扱う対象または問いを特定できる句にする。
- 「例に戻す」「読み直す」のような作業だけを示す見出しを避ける。
- 説明型長文では、結論を決め台詞として言い切る見出しを繰り返さない。
- 結論型見出しが検索性と判断速度を高める実務文書では、結論を見出しにしてよい。
- 見出しへ罫線やダッシュで二要素を詰め込まない。自然な名詞句、疑問形、助詞でつないだ句を使う。
- コラム見出しには「基礎」「補足」のような種別名だけでなく、内容を特定できる語を使う。

## 読者への誠実さ

- 例が作為的に見える可能性を隠さない。
- 例が現実にも起こり得る根拠は、確認できる一般的事実、通説、読者が検証できる経験則へ求める。
- 確認していないことを、確認したかのように滑らかに書かない。
- 主張を支える例が一部だけなら、主張の範囲を例に合わせる。
